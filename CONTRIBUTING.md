# Contributing to Beyond 90

Thanks for helping. The project is small on purpose: the scoring engine has no runtime dependencies and every formula has a test.

## Ground rules

- **No customer data, ever.** Issues, tests and examples use mock data only. The example account is generated by `examples/generate_examples.py`.
- **Formulas change only with a test and a note in `SPEC.md`.** A score that moves silently is a bug.
- **Denominators come from independent sources**, never from the platform's own inventory. That is the point of the tool.
- Keep the runtime dependency-free (Python standard library, 3.11+). The browser app loads nothing from a third party at run time and sends nothing anywhere; a test checks both.
- Free text from customer files is untrusted. Escape it in HTML and rely on the loader's cleaning for Markdown; `tests/test_hostile.py` shows how it is checked.

## Development

```
python -m venv .venv && . .venv/bin/activate
pip install --require-hashes -r requirements/dev.txt && pip install --no-deps -e .
python -m pytest -q
ruff check src tests examples site scripts && mypy src          # mypy runs in strict mode
beyond90 score examples/portfolio/northwind --format text
```

The tools are pinned with hashes in `requirements/` (`dev.txt`, `e2e.txt` for the browser test, `audit.txt` for the workflow audit) and in `site/npm/package-lock.json`. Ruff includes the security rules (`S`); an exception is written next to the line, with the reason.

The browser app (`site/`) has no build step beyond `site/build_site.py`. Lint it with `site/npm/node_modules/.bin/eslint --config site/npm/eslint.config.mjs site` (no `eval`, no HTML sinks), test its data model and vault with `node --test site/test/*.test.mjs`, and the whole app with `python site/e2e.py _site` (see [docs/app.md](docs/app.md)). Workflows are audited with `zizmor .github/workflows`. Outputs under `docs/example/` are generated: run `python examples/generate_outputs.py` after changing a report, and commit the result (a test fails when they are stale).

## Pull requests

1. Open an issue first for new stages, metrics or catalogue changes.
2. Add or update tests. Run `python -m pytest -q`, and the Node and browser tests if you touched `site/`.
3. Update `docs/` when the data format or the report changes.
4. Catalogue changes (`src/beyond90/data/*.json`) must keep `since` versions monotonic: a module never disappears from an older ceiling.
